GitHub PAT・API 使い方

個人用アクセストークン (personal access token, PAT) の作り方・使い分けと、REST API・GraphQL API を curl・gh で呼ぶときの決まりごと（REST の API バージョン 2026-03-10 時点）

ざっくり言うと
  • PAT は自分の権限の範囲で API や HTTPS の Git を使うための鍵で、できる限り fine-grained を使う。
  • API は REST と GraphQL の 2 つで、同じトークンで呼べるが、片方にしかない機能もある。
  • 単発の操作は REST、入れ子のデータをまとめて読むなら GraphQL を使い、PAT には必ず有効期限を付ける。

どのトークンを使うか

手元のターミナルで Git・gh を使いたいgh auth loginGitHub CLI か Git Credential Manager に任せる。PAT を作らずに済む
Actions のワークフローから API を呼びたいGITHUB_TOKENジョブごとに自動で発行。permissions: で権限を絞る
自分のスクリプト・ツールから API を呼びたいfine-grained PATリポジトリと権限を絞れる。できないことがあれば classic
組織のための長く動く連携・BotGitHub App個人に紐づかず、トークンは 1 時間で切れる。レート制限も増える

トークンの種類と接頭辞

トークンは先頭の接頭辞 (prefix) で種類が分かる。漏えいの検出やログのマスクに使える。

種類接頭辞有効期間主な使い道
fine-grained PATgithub_pat_作成時に選ぶ（最長 1 年か、無期限）自分のスクリプト・ツール
PAT (classic)ghp_作成時に選ぶ（無期限も可）fine-grained でできない操作
OAuth アプリのトークンgho_長期OAuth アプリがユーザーとして呼ぶ
GitHub App のユーザー用トークンghu_8 時間（既定）App がユーザーの代わりに呼ぶ
GitHub App のインストール用トークンghs_1 時間App 自身として呼ぶ（GITHUB_TOKEN もこの仕組み）
GitHub App のリフレッシュトークンghr_6 か月ghu_ の更新

ghs_ は 2026 年に、約 520 文字・ドット入りの JWT 形式（ghs_APPID_JWT）へ移行済み。「ghs_ + 36 文字」のような正規表現や、40 文字前提の DB 列・マスク処理は見直す。GitHub は形式で検証せず中身の分からない文字列として扱うよう勧めており、DB の列は 520 文字以上を入れられるようにする。

fine-grained と classic の違い

項目fine-grainedclassic
届く範囲選んだ 1 つのリソース所有者（ユーザーか組織）だけ。リポジトリも個別に選べる自分が触れる全リポジトリ（個人・所属組織すべて）
権限の指定権限ごとに Read / Read and write（GitHub App と同じ権限の体系）repo などの大まかなスコープ
組織の承認組織が承認制にできる。承認待ちの間は公開リソースの読み取りだけ承認の仕組みなし（組織は classic を禁止できる）
作れる数50 個まで上限の記載なし
共通持ち主の権限を超えない。持ち主がアクセスを失うと使えなくなる。1 年使わないと自動で削除。公開リポジトリや Gist に push すると自動で失効

fine-grained PAT はまだ次のことができない（GitHub は順次ふさぐとしている）。ここに当たるときだけ classic を使う。

  • メンバーでない公開リポジトリへの貢献（fork 先への書き込みなど）
  • 外部コラボレーター・リポジトリのコラボレーターとして参加しているリポジトリへの貢献
  • 複数の組織に 1 つのトークンでまたがってアクセスする
  • GitHub Packages へのアクセス
  • Checks API の呼び出し
  • ユーザーアカウントが持つ Projects へのアクセス

ほかに、classic でしか使えない REST API のエンドポイントが一部ある。各エンドポイントのリファレンスに、使えるトークンの種類が書いてある。

スコープできること
（なし）公開情報の読み取りだけ
repo非公開を含むリポジトリへのフルアクセス。HTTPS の Git に使うならこれ
public_repo公開リポジトリだけ
workflow.github/workflows/ のファイルの追加・更新。無いとワークフローを含む push が拒否される
read:org / admin:org組織・チームのメンバーの読み取り ／ 組織の管理
read:packages / write:packagesGitHub Packages の取得 ／ 公開
gistGist の書き込み
delete_repo管理者であるリポジトリの削除

トークンが持つスコープはレスポンスヘッダー x-oauth-scopes、その API が求めるスコープは x-accepted-oauth-scopes で分かる（curl -I で確認）。

fine-grained PAT を作る

  1. 設定を開く右上のアイコン → Settings → 左の Developer settings → Personal access tokens → Fine-grained tokens → Generate new token
  2. 名前と有効期限Token name と Expiration を入れる。組織のポリシーで上限があると、それより長くできない
  3. リソース所有者Resource owner に自分か組織を選ぶ。fine-grained を禁止している組織は出てこない。承認制の組織なら理由を書ける
  4. リポジトリRepository access で必要最小限を選ぶ（Only select repositories なら個別に指定）。公開リポジトリの読み取りは常に付く
  5. 権限Permissions で必要な権限だけ Read / Read and write にする。Metadata の読み取りは必ず付く
  6. 発行してすぐ保管Generate token。値はこの画面でしか見られないので、パスワードマネージャーや Secrets に入れる

作成画面は URL のパラメータで中身を埋めておける。チームに「この権限で作って」と渡すときに便利（最後は本人が確認して発行する）。

https://github.com/settings/personal-access-tokens/new
  ?name=Repo-reading+token
  &description=Just+contents:read
  &target_name=octodemo      # リソース所有者
  &expires_in=45             # 日数（1〜366）か none
  &contents=read             # 権限名=read|write|admin（権限による）

classic は Tokens (classic) → Generate new token (classic) で作り、Note・Expiration・スコープを選ぶ。SAML SSO の組織で使うなら、作ったあとトークンごとに SSO の承認 (Configure SSO) が要る。

PAT を使う

export GH_PAT=github_pat_xxxxxxxx   # 履歴に残したくないなら read -s GH_PAT

# 自分の情報（-i でヘッダーも表示 → レート制限やスコープが見える）
curl -i https://api.github.com/user \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_PAT" \
  -H "X-GitHub-Api-Version: 2026-03-10"

# Issue を作る（fine-grained なら Issues: Read and write が必要）
curl -X POST https://api.github.com/repos/OWNER/REPO/issues \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer $GH_PAT" \
  -H "X-GitHub-Api-Version: 2026-03-10" \
  -d '{"title":"バグ報告","body":"再現手順…","labels":["bug"]}'
gh auth login                       # ブラウザでログイン（PAT 不要）
gh auth status                      # ログイン状態・スコープを確認
echo "$GH_PAT" | gh auth login --with-token   # PAT でログイン

# 環境変数で渡す（保存済みのログインより優先。GH_TOKEN → GITHUB_TOKEN の順）
GH_TOKEN=$GH_PAT gh api user

# {owner} {repo} は今いるリポジトリ（か GH_REPO）で置き換わる
gh api repos/{owner}/{repo}/issues --jq '.[].title'
gh api repos/{owner}/{repo}/issues -f title='バグ報告' -f body='…'   # パラメータがあると POST
gh api -X PATCH repos/{owner}/{repo}/issues/12 -f state=closed
gh api user/repos --paginate --jq '.[].full_name'             # 全ページ

-f は文字列、-F は true・false・null・数値を JSON の型に変換し、@file でファイルから読む。GitHub Enterprise Server 向けは GH_ENTERPRISE_TOKEN と --hostname。

# 推奨: gh に Git の認証を任せる
gh auth setup-git

# PAT を直接使うなら、パスワードを聞かれたところに PAT を貼る
git clone https://github.com/OWNER/REPO.git
Username: your-github-name     # ユーザー名は省略できない
Password: github_pat_xxxxxxxx  # ← アカウントのパスワードではなく PAT

# SSH の remote には使えない。HTTPS に切り替える
git remote set-url origin https://github.com/OWNER/REPO.git

URL に https://TOKEN@github.com/… と埋め込むと .git/config やシェル履歴に残る。資格情報ヘルパー（Git Credential Manager・gh auth setup-git）に保存させる。

permissions:            # 書かない権限は none になる
  contents: read
  issues: write

jobs:
  comment:
    runs-on: ubuntu-latest
    steps:
      - run: gh issue comment "$NUMBER" --body "Thanks!"
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}   # gh には GH_TOKEN で渡す
          GH_REPO: ${{ github.repository }}
          NUMBER: ${{ github.event.issue.number }}

      # 別リポジトリを触るなら、PAT を Secrets に入れて使う
      - run: gh api repos/OTHER_OWNER/OTHER_REPO/dispatches -f event_type=sync
        env:
          GH_TOKEN: ${{ secrets.CROSS_REPO_PAT }}
  • GITHUB_TOKEN はジョブの開始時に発行され、ジョブが終わると失効する（GitHub ホストのランナーでは最長 6 時間。セルフホストでは更新できるのは 24 時間まで）。手動で失効させる方法はない
  • 届くのはワークフローがあるリポジトリだけ。ほかのリポジトリには PAT か GitHub App のトークンを使う
  • GITHUB_TOKEN で起こしたイベント（push・Issue 作成など）では、原則として新しいワークフローは動かない（workflow_dispatch・repository_dispatch は例外）。PR の作成・更新（opened・synchronize・reopened）は、書き込み権限のある人が承認すると動く。承認なしで連鎖させたいなら PAT か App のトークンを使う
import { Octokit } from 'octokit';

const octokit = new Octokit({ auth: process.env.GH_PAT });

const { data: me } = await octokit.request('GET /user', {
  headers: { 'X-GitHub-Api-Version': '2026-03-10' },
});

// 全ページを 1 つの配列で受け取る
const issues = await octokit.paginate('GET /repos/{owner}/{repo}/issues', {
  owner: 'OWNER', repo: 'REPO', state: 'open', per_page: 100,
});

Octokit は Accept と User-Agent を自動で付ける。

REST と GraphQL

GitHub の API は 2 つある。どちらも同じトークン（PAT・GITHUB_TOKEN・App のトークン）で呼べ、gh・curl・Octokit から使える。違いは「返す中身を誰が決めるか」。

REST

URL がたくさんある: https://api.github.com/…

  • URL ごとに返す中身が決まっていて、使わないフィールドも返る
  • 関連データは URL を変えて何回も呼ぶ
  • 操作は HTTP メソッド（GET・POST・PATCH・DELETE）で表す
  • レート制限は回数で数える
GET /repos/cli/cli
GET /repos/cli/cli/issues?per_page=3
GET /users/{login}   # 作者ごとに…

GraphQL

入口は 1 つ: POST https://api.github.com/graphql

  • 欲しいフィールドをクエリに書くと、その形のまま返る
  • 入れ子のデータも 1 回で取れる
  • 読み取りは query、書き込みは mutation
  • レート制限はクエリの重さ（ポイント）で数える
query {
  repository(owner: "cli", name: "cli") {
    issues(first: 3) { nodes { title author { login } } }
  }
}

片方にしかない機能

大部分は重なっているが、一方にしかない機能もある。使う前に、目的の機能がどちらのリファレンスにあるかを確かめる。

機能RESTGraphQL
Discussionsなし取得・作成・編集・削除
Projects一覧・取得、アイテムの追加・削除、フィールドの値の更新（2025 年に追加）。その後フィールドの追加もできるようになった上に加えて、プロジェクトそのものの作成・削除と、フィールドの削除
Packages（コンテナ・npm など）あり新しい仕組みのレジストリ（コンテナ・npm など）のデータは返さない

傾向として、Actions（実行・Secrets・ログ）や Webhook の設定のような管理系は REST が中心、Issue・PR・リポジトリをまたいでまとめて読む用途は GraphQL が得意。

使い分けの目安

やりたいこと向いている方理由
Issue を 1 件作る・ファイルを 1 つ取るREST1 回で済み、curl でもすぐ書ける
一覧画面・集計（リポジトリ → Issue → 作者・コメント数）GraphQL何回も呼ぶ代わりに 1 回で取れ、余計なデータも来ない
Actions・Secrets・Webhook の操作REST多くは REST にしかない
Discussions・プロジェクト自体の作成GraphQLGraphQL にしかない

混ぜて使ってよい。REST のレスポンスの node_id は GraphQL の id と同じもので、両方の API の間で受け渡せる。

ヘッダーAccept・X-GitHub-Api-Version・User-Agent
api.github.comパスの {owner} などは実際の値に置き換える
レスポンスのヘッダーx-ratelimit-*（残り回数）・link（次のページ）
ヘッダー値メモ
AuthorizationBearer TOKENtoken TOKEN もたいてい通るが、JWT（App の認証）は Bearer だけ

API バージョン

バージョン状態
2026-03-10最新。サポート終了日は未定
2022-11-28ヘッダーを省いたときの既定。2028-03-10 にサポート終了

2026-03-10 に上げるときに引っかかりやすい破壊的変更（全体の一覧は参考の「Breaking changes」）:

  • GET /rate_limit の rate が無くなった → resources.core を読む
  • ワークフローの手動実行（POST …/dispatches）が 204 ではなく、実行の情報付きの 200 を返す
  • Issue・PR の単数の assignee が無くなった → assignees 配列を読む
  • PR の merge_commit_sha、リポジトリの has_downloads が無くなった
  • ディレクトリ一覧の中のサブモジュールが type: "submodule" になった（以前は file）

必要な権限は、各エンドポイントのリファレンスの「Fine-grained access tokens for …」の欄に書いてある。足りないと 403 か 404 になる。

REST のページネーション

  • 一覧系は per_page（多くは最大 100）と page で区切って返す。100 を超えて指定してもエラーにならず、黙って 100 に下げられる
  • 次のページはレスポンスの link ヘッダーの rel="next" の URL を使う（first・prev・last もある）。URL を自分で組み立てない。before・after で区切るエンドポイントもあるため
  • まとめて取るなら gh api --paginate（--slurp で 1 つの配列に）か octokit.paginate()
link: <https://api.github.com/repositories/1300192/issues?page=2>; rel="next",
      <https://api.github.com/repositories/1300192/issues?page=515>; rel="last"

GraphQL API の使い方

  • エンドポイントは POST https://api.github.com/graphql の 1 つだけ。本文は {"query": "…", "variables": {…}} の JSON
  • REST の X-GitHub-Api-Version は使わない。変更はスキーマの非推奨 → 削除として告知される（GraphQL の「Breaking changes」）
  • ドキュメントにあった GraphQL Explorer は 2025 年 11 月に廃止。試すなら gh api graphql か、好きな GraphQL クライアントを https://api.github.com/graphql に向ける
# 変数は -F / -f で渡す（query と operationName 以外は全部 GraphQL の変数になる）
gh api graphql -F owner='{owner}' -F name='{repo}' -f query='
  query($owner: String!, $name: String!) {
    repository(owner: $owner, name: $name) {
      stargazerCount
      issues(first: 10, states: OPEN, orderBy: {field: CREATED_AT, direction: DESC}) {
        totalCount
        nodes { number title author { login } comments { totalCount } }
      }
    }
  }' --jq '.data.repository.issues.nodes[] | "\(.number) \(.title)"'

接続（issues などの一覧）には必ず first か last（1〜100）を付ける。

GraphQL の書き込みは「対象の ID（ノード ID）を引く → その ID を mutation に渡す」の 2 段階になることが多い。REST の POST /repos/OWNER/REPO/issues なら 1 回で済む。

# 1. リポジトリの ID を引く（REST の node_id と同じ値）
REPO_ID=$(gh api graphql -F owner='{owner}' -F name='{repo}' -f query='
  query($owner: String!, $name: String!) { repository(owner: $owner, name: $name) { id } }' \
  --jq '.data.repository.id')

# 2. その ID で Issue を作る
gh api graphql -f repo="$REPO_ID" -f title='バグ報告' -f query='
  mutation($repo: ID!, $title: String!) {
    createIssue(input: {repositoryId: $repo, title: $title}) { issue { number url } }
  }'

ページ送りはカーソル方式。pageInfo { hasNextPage endCursor } を取り、次は after: endCursor で続きを取る。gh api graphql --paginate を使うなら、クエリに $endCursor: String 変数と pageInfo { hasNextPage endCursor } が要る。

gh api graphql --paginate -f query='
  query($endCursor: String) {
    viewer {
      repositories(first: 100, after: $endCursor) {
        nodes { nameWithOwner }
        pageInfo { hasNextPage endCursor }
      }
    }
  }' --jq '.data.viewer.repositories.nodes[].nameWithOwner'
curl https://api.github.com/graphql \
  -H "Authorization: Bearer $GH_PAT" \
  -d '{"query": "query { viewer { login } }"}'

# 変数付き
curl https://api.github.com/graphql \
  -H "Authorization: Bearer $GH_PAT" \
  -d '{"query": "query($n: Int!) { viewer { repositories(first: $n) { nodes { name } } } }",
       "variables": {"n": 5}}'

クエリの文字列の中で改行するなら \n にエスケープする。長いクエリは gh か GraphQL クライアントのほうが楽。

GraphQL の制限

項目内容
1 時間の上限ユーザー（PAT）5,000 ポイント。App のインストールは REST と同じく 5,000〜12,500、GITHUB_TOKEN はリポジトリごとに 1,000。Enterprise Cloud では App のインストールが 10,000、GITHUB_TOKEN が 15,000。REST とは別の枠
ポイントの数え方各接続が first/last の上限まで返すと仮定して必要なリクエスト数を足し、100 で割って丸める（最低 1）
1 回のクエリノードは合計 50 万まで。10 秒を超えると打ち切られ（502・504）、ポイントも余分に引かれる
短時間の制限1 分に 2,000 ポイントまで（query は 1、mutation は 5 ポイント）。同時 100 リクエストは REST と合算
残りを見るヘッダーの x-ratelimit-*（x-ratelimit-resource は graphql）か、クエリに rateLimit { cost remaining resetAt } を足す
 
query {
  rateLimit { limit cost remaining resetAt }   # このクエリが何ポイントかも分かる
  viewer { login }
}

上限に達しても、ステータスは 200 のまま本文に errors が入る。GraphQL は一部だけ失敗して data と errors が両方返ることもあるので、200 でも必ず errors を確かめる。

  • 同時に 100 リクエストまで（REST と GraphQL の合計）
  • 1 分あたり REST は 900 ポイントまで。GET などは 1、POST・PATCH・PUT・DELETE は 5 ポイント
  • 何かを作るリクエストは 1 分に 80・1 時間に 500 まで（Web 画面での操作も数える）
  • 状態を確かめる方法はない。超えたら retry-after に従う
ヘッダー意味
x-ratelimit-limit1 時間の上限
x-ratelimit-remaining今の枠で残っている回数
x-ratelimit-used今の枠で使った回数
x-ratelimit-reset枠が戻る時刻（UTC の epoch 秒）
x-ratelimit-resourceどの枠で数えたか（core・search など）
retry-after短時間の制限に当たったとき、待つ秒数

403・429 が返ってきたら

  1. retry-after を見るあれば、その秒数だけ待つ
  2. remaining が 0 か見るx-ratelimit-remaining: 0 なら x-ratelimit-reset の時刻まで待つ
  3. どちらも無ければ 1 分待つそれでも続くなら、待ち時間を倍々にして (exponential backoff) 決めた回数で諦める
  4. 待たずに叩き続けない制限中にリクエストを続けると、連携ごと止められることがある

最後の手順だけ赤いのは「してはいけないこと」だから。

ステータスよくある原因
401トークンが間違い・期限切れ・削除済み

422送ったパラメータが不正（必須の欠け・値の誤り）

GraphQL は失敗してもステータスが 200 のことが多い。本文の errors を見る。問い合わせるときは、レスポンスの x-github-request-id を添える。

よくある誤解

admin:org のスコープを付ければ組織の管理ができる

トークンは持ち主の権限を超えない。組織のオーナーでない人の PAT に admin:org を付けても、管理の操作はできない。

無期限のトークンはずっと使える

1 年使われなかった PAT は自動で削除される。公開リポジトリや Gist に push されたものも自動で失効する。組織のポリシーで有効期限の上限がかかることもある。

GITHUB_TOKEN があれば同じ組織のほかのリポジトリも触れる

届くのはワークフローがあるリポジトリだけ。ほかのリポジトリには、そのリポジトリを選んだ fine-grained PAT か GitHub App のトークンを使う。

Issues の API では Issue だけが返ってくる

REST API では PR も Issue の一種として返る。PR には pull_request キーが付くので、それで見分ける。

REST と GraphQL はどちらでも同じことができる

大部分は重なっているが、Discussions は GraphQL だけ、Packages の新しい仕組みのレジストリ（コンテナ・npm など）のデータは REST だけ、のように片方にしかない機能がある。目的の機能がどちらのリファレンスにあるかを先に確かめる。

GraphQL なら 1 回で取れるのでレート制限を気にしなくてよい

GraphQL はクエリの重さでポイントを消費する。first: 100 を何段も入れ子にすると 1 回で大きく減る。rateLimit { cost } で重さを確かめる。

404 が返ったのでリソースは存在しない

非公開のものはトークンに権限が無いと 404 になる。fine-grained ならリソース所有者・リポジトリの選択・権限を見直す。
