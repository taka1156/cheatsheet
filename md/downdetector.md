# Downdetector 使い方

> Downdetector の仕組み、障害かどうかを確かめる手順、画面の読み方、他の情報源との組み合わせ、プランをまとめたチートシート

- URL: https://cs.taka1156.site/downdetector.html
- タグ: セキュリティ
- 日付: 2026-11-22

---

利用者からの「つながらない」という報告を集めて、Web サービス・通信会社・銀行などの障害をいち早く見せるサイト（2026-11 時点）

**ざっくり言うと**

- Downdetector は利用者の障害報告と SNS などの声を集め、普段より急に増えたサービスを障害として表示する。
- 公式発表より早く「自分だけか、みんなか」が分かるが、数字は報告した人の数で、影響の大きさや原因ではない。
- 公式のステータスページや Cloudflare Radar などの観測データと突き合わせて判断する。

## 仕組み

**報告を集める** サイト・アプリからの「問題がある」報告と、SNS などの声

**基準と比べる** サービスごと・時間帯ごとの「いつもの報告数」（過去 1 年の平均）を基準にする

**障害と判断** 基準を大きく上回る状態が続いたら、障害（incident）として表示

しきい値や重み付けの細かい中身は公開されていない。報告そのものの真偽は 1 件ずつ確かめず、量とパターンで判断している。

## 障害かどうか確かめる手順

1. **国のサイトを開く** 日本なら `downdetector.jp` 、アメリカなら `downdetector.com` 。サービスの一覧や報告数は国ごとに別々。
2. **サービスを検索する** サービス名で検索し、詳細ページを開く。トップには今報告が多いサービスが並ぶ。
3. **グラフを見る** 直近 24 時間の報告数の推移と、いつもの量（基準）を比べる。基準線を大きく超えた山があれば多くの人が困っている。
4. **何が起きているか見る** 「よく報告されている問題」（ログイン・アプリ・サーバー接続・Web サイトなど）の割合と、コメント・地図で、症状と地域を絞る。
5. **公式の情報と突き合わせる** サービスの公式ステータスページや公式 SNS で発表を確かめる。発表がまだなら、Downdetector の山が先に来ていることが多い。
6. **自分も困っていれば報告する** サービスのページにある報告ボタンから症状を選んで報告する。報告が集まるほど、ほかの人の判断材料になる。

## 画面の読み方

| 部分 | 見方 |
| --- | --- |
| 報告数のグラフ | 山の高さは「その時間に報告した人の数」。夜中の小さな山と、昼の大きな山は同じ重みではないので、基準との差で見る |
| 基準（いつもの量） | 時間帯ごとに違う。利用者の多いサービスほど、平常時でもある程度の報告がある |
| よく報告されている問題 | 症状の内訳。「ログインだけ」なら認証まわり、「すべて」ならネットワークや基盤の障害を疑う手がかり |
| 障害マップ | 報告の多い地域。通信会社の障害では、地域が偏っていれば局所的な設備の問題の可能性がある |
| コメント | 症状の具体例やエラーメッセージ。ただし推測や誤情報も混じる |

## ほかの情報源と組み合わせる

| 情報源 | 分かること | 弱いところ |
| --- | --- | --- |
| Downdetector | 利用者がどう困っているか（症状・地域）。公式発表より早いことが多い | 原因は分からない。報道や SNS の話題で報告が膨らむことがある |
| 公式ステータスページ | 事業者が認めた障害、影響範囲、復旧見込み | 発表が遅れる・小さめに書かれることがある |
| [Cloudflare Radar](https://cs.taka1156.site/md/cloudflare-radar.md) | 国・AS 単位の通信量の落ち込み、BGP の異常、Outage Center の原因の記録 | 個々のアプリの不具合（ログインだけ失敗など）は見えない |
| 自前の監視（外形監視・APM） | 自社サービスの正確な状態 | 利用者側の回線や、依存先のサービスの障害は見落としやすい |

たとえば「Downdetector で通信会社 A の報告が急増」＋「Radar で A の AS の通信量が落ちている」なら回線側の障害、「報告は増えたが Radar は平常」ならアプリやサービス側の不具合を疑う。

## 運用・セキュリティでの使いどころ

| 場面 | 使い方 |
| --- | --- |
| 問い合わせが急に増えた | 自社サービスや依存先（クラウド・決済・認証・CDN）の Downdetector を見て、原因が外にあるか切り分ける |
| 自社のサービスの障害 | 自社の監視が気づく前に利用者の報告が増えることがある。症状の内訳とコメントで影響を把握する |
| DDoS や大規模障害のニュース | 本当に利用者に影響が出ているか、どの地域かを確かめる。報道だけで判断しない |
| 障害の振り返り | 利用者が困り始めた時刻・ピーク・収まった時刻の目安として、社内の記録と並べる |

## よくある誤解

✗ 誤解: 報告数は障害で困っている人の数だ

✓ 正しくは: 数えているのは「Downdetector を開いて報告した人」だけ。サービスの利用者数・知名度・報道の量で大きく変わるので、サービスどうしの数字を比べて規模の大小は言えない。

✗ 誤解: 報告が減ったら復旧した

✓ 正しくは: みんなが見に来なくなっただけ（夜になった、諦めた）でも報告は減る。復旧は公式発表や自分での確認で判断する。

✗ 誤解: Downdetector に何も出ていなければ障害はない

✓ 正しくは: 利用者の少ないサービスや一部の地域だけの障害は、基準を超えず表示されないことがある。載っていないサービスもある。

✗ 誤解: グラフの山を見れば原因まで分かる

✓ 正しくは: 分かるのは「困っている人が増えた」ことだけ。依存先の障害で巻き添えになったサービスにも山ができる（例: CDN やクラウドの障害で多数のサービスに同時に山）。原因は公式発表や観測データで確かめる。
